# 消费者购物网站设计

## 意图

在仓库中新增独立消费者前端 `web/mall-web`，让消费者可以发现并购买平台商家的商品。消费者站与现有 `web/mall-admin` 分开运行和部署，复用现有 API、账号、认证与交易规则，不承载平台管理或商家工作台。

## 目标

- 未登录访客可以浏览已审核商品和分类、搜索商品、查看商品详情。
- 登录消费者可以维护购物车和收货地址，按店铺拆分提交订单，查看订单并执行后端允许的操作。
- 支持桌面和移动浏览器，购买路径清楚，价格和订单状态使用后端数据。
- 复用现有 React、TypeScript、Umi Max、Ant Design 技术栈和 API 代理习惯，同时提供面向消费者的自定义页面布局。

## 非目标

- 不把商家管理、平台审核、财务后台或商城管理界面放入消费者站。
- 不接入真实支付、退款渠道、物流轨迹、营销券、评价、收藏或搜索引擎。
- 不实现后端尚不支持的地址编辑、默认地址、规格选择、运费和商品图片上传。

## 现有能力与约束

- 后端公开提供 `/v1/market/catalog`（筛选 `name`、`categoryId`，分页 `current`、`pageSize`）和 `/v1/market/categories`；登录后提供购物车、地址、结算、订单与动作接口。
- `/register`、`/login`、`/captcha` 和 token 认证已存在，可供新前端复用。
- 注册需要图形验证码，注册成功后不会自动登录；登录在连续失败达到阈值后才要求验证码。
- 原始 API 响应为 `{ code, message, data }`。管理站通过响应拦截器转换为 `{ success, data, errorCode, errorMessage }`，新站必须明确适配原始包络或实现自己的等价拦截器。
- 结算服务端重新核价、按店铺拆单、要求 `requestKey` 幂等，并从当前用户身份确定购物车和地址归属。
- 订单操作支持取消、沙箱付款、确认收货和发起售后。真实支付未接入；生产模式拒绝沙箱付款。
- 商品公开列表支持名称和分类筛选、分页，但现有公开接口没有按商品 ID 读取详情的路径。因此首期需要新增 `GET /v1/market/catalog/:id`，返回同一公开可见性规则下的商品详情；冻结店铺、下架或未审核商品不能通过此接口读取。
- 商品只有图片 URL；首期不做上传。当前没有商家店铺详情、评价和丰富内容运营接口。

## 消费者主流程

1. 访客进入首页，浏览分类和商品，按名称搜索或分类筛选。
2. 打开商品详情，确认图片、说明、价格和库存。
3. 点击加入购物车；未登录时转到登录/注册，成功后回到原商品或购物车。
4. 在购物车选择商品和数量，选择或新增收货地址。
5. 提交结算时生成新的 `requestKey`；重复网络重试复用同一 key，用户修改购物车 ID 集合或地址后生成新 key。单次最多提交 100 个不重复购物车项 ID。
6. 展示按店铺拆分后的订单。订单默认待付款；仅当后端上下文报告沙箱开启时展示明确标注的“开发沙箱付款”，不声称产生真实扣款。消费者可按状态取消、确认收货或申请售后。

## 页面与路由

- `/`：商城首页/商品目录；分类入口、搜索、商品卡片、分页、空结果和错误重试。
- `/product/:id`：商品详情、库存与加入购物车；处理商品失效和下架。
- `/cart`：购物车增减数量、选择结算商品、移除商品、金额汇总和前往结算。
- `/checkout`：选择收货地址、查看选中商品与提交确认；服务端失败时保留可恢复的表单状态。
- `/orders`：消费者订单列表、状态筛选和订单详情；展示拆分后的各店订单。
- `/account/addresses`：地址列表、新增、删除；不展示暂不支持的编辑和默认地址功能。
- `/user/login`、`/user/register`：账号登录、邮箱注册和图形验证码；支持登录后回跳。

共享消费者站头部（品牌、搜索、购物车入口、账户入口）和页脚。登录后的路由仍允许返回商品目录。受保护 API 返回未授权时清除失效 token 并引导重新登录。

## 技术方案与取舍

### 方案 A（推荐并选定）：独立 Umi Max 前端

新增 `web/mall-web`，沿用仓库已有 React/TypeScript/Umi Max 及 Ant Design 依赖体系，建立消费者专属路由、布局、请求封装和页面。优点是开发/部署边界独立，同时减少技术栈分叉；缺点是与管理站存在少量依赖和 API 类型重复。

### 方案 B：把消费者页面放进 `web/mall-admin`

可复用现有依赖和部分 API 模块，但会让消费者路由、登录状态和消费者视觉结构与运营后台耦合，不符合独立购物网站的目标。

### 方案 C：独立 Vite 项目

运行和打包更轻，但会引入第二套前端构建、路由和代理约定。首期没有足够收益抵消维护差异。

已选择方案 A；新站使用独立消费者布局，不复用 Pro 管理端布局。可复用后端接口和认证约定；共享 UI/类型库暂不抽取，避免首期扩大改造范围。

## 请求、身份和状态处理

- 新站定义自己的轻量 API 类型和请求层，不跨目录导入 `mall-admin` 源文件。
- 请求层添加 Bearer token，直接适配后端 `{ code, message, data }` 响应；非 2xx 统一显示可理解的错误提示，不依赖管理站的响应转换格式。
- 登录持久化 access token 与可用的 refresh token 到 `localStorage`；access token 失效时最多调用一次 `/refresh` 并重试原请求，refresh 失败后清理令牌并跳转登录；退出时调用 `/logout` 并清理本地令牌。
- 公开目录不要求登录；购物车、地址、订单和结算要求登录。保存回跳目标，登录后回到消费者原流程。
- 结算金额只展示服务端返回的订单金额；同一用户对相同地址和相同购物车 ID 集合进行网络重试时复用幂等 key，地址或 ID 集合变化时生成新 key。
- 沙箱支付只有在 API context 的 `sandboxPayment` 为真时显示，并在按钮、确认反馈和订单说明中持续明确“开发沙箱付款，不产生真实扣款”。关闭时显示待付款订单及后端可执行动作，不提供伪造支付成功的 UI。
- 列表请求使用后端分页参数并做请求过期保护；订单列表已带订单商品 `items`，详情可在站内展示，不依赖单订单详情接口。对加载、无数据、网络失败、会话过期、商品失效、库存不足分别设计可恢复状态。

## 后端配套变更

- 新增公开 `GET /v1/market/catalog/:id`，`data` 返回单个 `Product`，响应沿用统一响应包络；找不到或不符合公开目录可见性时返回 404。
- 查询必须复用目录的商品审核状态、商品上下架和店铺正常状态约束；不能让猜测 ID 绕过公开目录权限。
- 新站仅依赖本次明确列出的现有功能和此商品详情接口，不新增用户身份或交易规则。

## 验收条件

- 桌面与窄屏均可完成“浏览 → 详情 → 登录/注册 → 购物车 → 地址 → 结算 → 订单”的主流程。
- 访客能查看公开目录，受保护操作跳转登录并能回到原目标。
- 商品详情接口不能读取未审核、下架或冻结店铺商品。
- 结算按服务端金额工作，重复提交不重复建单；库存或地址错误有明确反馈。
- 沙箱开关关闭时不显示开发沙箱付款动作；开启时付款文案不暗示真实资金处理。
- 订单操作只展示并调用对应状态允许的后端动作。
- 新站有独立开发、测试和生产构建命令；代理 `/v1/` 与认证路径到 API 服务。

## 尚待实现者决定

- 商品卡片的具体品牌视觉、颜色、字体和图片比例；默认采用简洁、可信、以商品图和购买动作为主的消费者电商风格。
- 是否在一个轻量确认页完成地址选择和提交，或将其拆为购物车中的结算弹层；默认使用独立结算页，以降低移动端拥挤并清楚确认拆单信息。
- 首期不增加运营内容配置，首页只使用现有分类和商品目录数据。
